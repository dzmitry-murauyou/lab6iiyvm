## 2. Требования варианта 8

| № | Требование из PDF | Реализация | Проверка |
|---|---|---|---|
| 1 | Передача файла от Peripheral к Central (или наоборот) через GATT-характеристику | Центральный (Central) отправляет, приёмник (Peripheral) принимает — направление Central → Peripheral, что вариант допускает; сервис `A1B2…4C5D`, характеристики `Control`/`Data`/`Status` | код: `ReceiverMain`, `TryConnect`, `SendFileOnce`; модель передачи в тестах |
| 2 | Write Without Response для максимальной скорости | `WriteBlock` → `WriteValueWithResultAsync(..., GattWriteOption::WriteWithoutResponse)`; размер блока = `MTU − 3 − 4` (4 байта — смещение) | тест «Размеры блоков»: MTU 23 → 16 Б, MTU 517 → 510 Б |
| 3 | Контроль целостности CRC32 | отправитель считает CRC до передачи (`Crc32File`), приёмник — после записи на диск (`FinishSession`), сравнение и вердикт `OK`/`MISMATCH` | тест CRC: эталонный вектор `CBF43926`, потоковый = разовый, изменение байта меняет сумму |
| 4 | Подтверждение приёма (ACK) | `Status` (notify): `ACK\|смещение` практически на каждый блок (192 байта / 10 мс; отдельный поток) плюс по запросу `SYNC`; отправитель держит адаптивное окно 2…4 КБ (4…32 блока) и откатывается к подтверждённой позиции, если ACK нет 1,5 с | тесты «Строки протокола», «Модель передачи» (5 % потерь, 3 % дубликатов) |
| 5 | Прогресс, скорость, оценка времени | `PublishProgress` + `SampleSpeed` (скользящее окно 1,5 с), ETA = остаток / скорость; в UI — полоса, «Передано», «Скорость», «Осталось» | код + тесты модели (счётчики блоков/байт) |
| 6 | Обработка разрыва соединения | `OnDeviceConnectionChanged`, `OnSubscribersChanged` (сторона приёмника), журнал, статус «Связь потеряна — восстановление…» | модель передачи: сценарий «обрыв на середине» |
| 7 | Возобновление передачи | сеанс приёмника сохраняется (файл и смещение), повторный `START` возвращает `READY\|смещение`, отправитель продолжает с этого байта (до 6 попыток переподключения) | модель: «возобновление» и «обрыв + потери» — CRC сходится |

## 4. Найдено и исправлено в ходе самопроверки

| Дефект | Последствие | Исправление |
|---|---|---|
| Передача замирала на первом блоке (≈510 Б) и не шла дальше при MTU 517 | `cursor` откатывался к подтверждённой позиции на каждом шаге, хотя курсор впереди ACK — это норма для окна; блок переписывался бесконечно | откат только по отсутствию ACK (1,5 с), в норме курсор просто идёт вперёд |
| Маленький файл (< 8 КБ) завершался ошибкой: последний `ACK` не приходил (порог 8 КБ / 100 мс не срабатывал) | «последние блоки не подтверждены» через 8 с, хотя файл уже принят | добавлена команда `SYNC`; отправитель запрашивает смещение перед `END` |
| Потеря первого `READY` | 12-секундное ожидание и обрыв | `START` повторяется до 3 раз по 4 с (команда идемпотентна) |
| Подключение к устройству со случайным адресом (смартфоны, трекеры) | `FromBluetoothAddressAsync(addr)` не находил устройство | сохраняется `BluetoothAddressType` из рекламы, используется нужная перегрузка |
| Двойной клик «Поиск»: второй вызов делал `join` живого потока | зависание UI | атомарный флаг `scan_active`/`recv_active` выставляется до запуска потока |
| Двойной клик «Отправить» | мог запустить вторую передачу | атомарный захват `send_busy` (compare-exchange) |
| Закрытие окна во время паузы восстановления связи | окно «висело» до 2 с | `SleepCancelable` — ожидание прерывается отменой |
| Состояние канала после отключения Central во время паузы | показывалось «Ожидание», хотя сеанс на паузе | `LinkPaused` при незавершённом сеансе |
| Перерисовка owner-draw кнопок 7 раз в секунду | лишняя нагрузка, мигание | маска состояний в `View::SetEnabled` с ранним выходом |
| Инструмент сборки | проект не открывался бы в VS, где собран ЛР5 | `v145` / `VCProjectVersion 18.0`, как в ЛР5 |

## 5. Что не проверено (и как проверить на месте)

| Пункт | Почему | Как проверить |
|---|---|---|
| Сборка MSVC + C++/WinRT | нет Windows SDK в песочнице | открыть `Lab6_BLE.vcxproj`, собрать x64 (см. README §4) |
| Роль Peripheral на конкретном адаптере | нужен реальный адаптер/драйвер | «Приёмник» → «Старт»; при отказе в журнале будет `Не удалось создать GATT-сервис: запрещено политикой` |
| Реальный обмен по BLE | нужны два устройства | сценарий из README §5 |
| Скорость и MTU | зависят от адаптеров | в карточке «Сеанс» отображается `MTU … · данные …` |
| Возобновление на живом разрыве | нужен физический разрыв | выключить/включить Bluetooth на приёмнике в середине передачи |

Чек-лист приёмочного прогона (10 шагов):

1. Приёмник: «Старт» → в журнале `GATT-сервис опубликован`.
2. Отправитель: «Поиск» → устройство с пометкой `• Lab6`.
3. «Подключить» → `Подключено: …, MTU …, блок данных …`.
4. Выбрать файл → «Отправить» → растут прогресс, скорость, счётчик ACK.
5. Дождаться `CRC32 … совпал` на обеих сторонах.
6. Сверить файлы на приёмнике (`Документы\Lab6_BLE`).
7. Повторить с файлом ~50 МБ (проверка ETA и скорости).
8. Малый файл (< 8 КБ) — проверка исправления с `SYNC`.
9. Обрыв связи в середине → автовосстановление → `продолжаем с …`.
10. «Отменить» в середине → `ABORT` на приёмнике, частичный файл сохранён.

## 6. Ограничения реализации (осознанные)

* Один Central на приёмник (сеанс один); второй Central получит `ERR`.
* Файл ≤ 4 ГиБ — смещение в кадре 32-битное.
* Приёмник пишет файл в `Документы\Lab6_BLE` (каталог не выбирается в UI).
* Режим «Peripheral → Central» (передача уведомлениями) не реализован: вариант
  требует Write Without Response, то есть отправляет всегда Central.
