# BLE-передача файла: построчный разбор команд

Разбор сделан по присланным `main.cpp` и `ble.cpp`. Сверка с репозиторием показала: во вложениях удалены только комментарии, исполняемый код тот же. Поэтому ссылки ниже открывают исходники в Git, а рядом указаны строки **во вложениях**. Исходники не заменены. Графика и отрисовка намеренно не разбираются.

## 1. Как вообще идёт разговор между ноутбуками

Приёмник (Peripheral) публикует GATT-сервис. Отправитель (Central) находит его и подписывается на уведомления `Status`. Приложение не создаёт сокет и не применяет Bluetooth Classic или Wi-Fi для файла.

| Характеристика | Кто пишет | Что идёт |
|---|---|---|
| `Control` | Отправитель | Текстовые команды `START`, `SYNC`, `END`, `ABORT` (UTF-8). |
| `Data`, `Data2…Data4` | Отправитель | Бинарные кадры с байтами файла. Это характеристики одного сервиса, не отдельные соединения. |
| `Status` | Приёмник | Уведомления `READY`, `ACK`, `DONE`, `ABORTED`, `ERR`. |

Пример последовательности для файла `test.bin` размером 300 байт. `1234ABCD` — условная контрольная сумма, в реальности её вычисляет код:

```text
Control → START|300|1234ABCD|test.bin
Status  ← READY|0
Data    → [смещение 0][байты 0…99]
Data    → [смещение 100][байты 100…199]
Data    → [смещение 200][байты 200…299]
Control → SYNC                        только если ещё нет итогового ACK
Status  ← ACK|300
Control → END|300|1234ABCD
Status  ← DONE|300|1234ABCD|OK|путь
```

`ACK|300` значит «байты `0…299` приняты без пропусков; следующий байт имел бы смещение 300». `OK` приходит отдельно, после проверки файла.

## 2. От команды пользователя до `START`

**Вложение `main.cpp:334, 452–482`** · [Обработчик команд](main.cpp#L348) · [Запуск отправки](main.cpp#L466)

1. `case ID_SEND` выбирает ветку отправки. `if (code == BN_CLICKED) SendFile();` вызывает её только на клик.
2. `GetWindowTextW(...)` получает путь. Если путь пустой, `BrowseFile()` даёт его выбрать. Если путь так и остался пустым, `return` прекращает запуск.
3. Если `current.connected` ложно, сначала требуется выбранное устройство. `engine_.Connect(DeviceIndex(sel))` запускает подключение; это ещё не подтверждение успешной связи.
4. `engine_.StartSend(path)` передаёт **путь**, не содержимое файла. `false` — движок не запустил задачу, а не результат проверки CRC.

**Вложение `ble.cpp:3153–3192`, `1874–1945`** · [`StartSend`](ble.cpp#L3196) · [`SendJob`](ble.cpp#L1917)

1. `StartSend` резервирует отправку через `send_busy.compare_exchange_strong`, чтобы не запустить две одновременно, проверяет путь и адрес назначения, запускает рабочий поток.
2. В `SendJob` строка `const std::uint32_t crc = Crc32File(path, &size, &cancel);` читает исходный файл, получает размер и CRC. `Crc32File` (во вложении с 326) обновляет CRC порциями, не загружая файл целиком.
3. Цикл `attempt` сначала дожидается завершения текущей попытки подключения, а если связи нет — вызывает `TryConnect(address, address_type)`. После подключения вызывает `SendFileOnce(path, name, size, crc)`.
4. `TryConnectWith` (вложение с 1033) открывает BLE-устройство, ищет сервис по UUID, находит характеристики и включает уведомления `Status`. На второй стороне `ReceiverMain` (вложение с 2640) создаёт тот же сервис, назначает обработчики и включает BLE-рекламу. [Подключение](ble.cpp#L1076) · [Запуск приёмника](ble.cpp#L2683)

## 3. `START` → `READY`: открытие или продолжение

**Вложение `ble.cpp:1606–1631`** · [`SendFileOnce`](ble.cpp#L1649)

```cpp
ResetInbox();
// Внутри цикла попыток:
if (!WriteControl(Format(L"START|%llu|%08X|%s", size, crc, name.c_str()))) {
    throw LinkLost("START не отправлен");
}
ready = WaitStatus(L"READY|", line, 4000);
```

- `ResetInbox()` очищает накопленные ответы перед новой попыткой.
- `Format` подставляет десятичный размер, CRC в шестнадцатеричном виде и имя. `WriteControl` (вложение с 1448) переводит команду в UTF-8 и вызывает `WriteValueWithResultAsync` с `WriteWithResponse`.
- Ответ на GATT-запись **не равен** `READY`: первый относится к записи характеристики, второй сообщает, что сделал файловый протокол. Если `READY` не пришёл, `START` можно повторить: всего до трёх отправок с ожиданием по 4 секунды.
- `ParseUll(line.substr(6))` отбрасывает `READY|` и получает смещение. Если оно больше размера, код заменяет его на ноль. `acked = offset` задаёт стартовую подтверждённую позицию.

**Вложение `ble.cpp:2044–2054`, `2290–2410`** · [`OnControlWrite`](ble.cpp#L2087) · [`HandleControl`](ble.cpp#L2333) · [`StartSession`](ble.cpp#L2350)

1. `GetDeferral()` удерживает обработку события на время получения запроса. `FromBuffer(request.Value())` копирует байты. На `WriteWithResponse` выполняется `request.Respond()`. Потом текст преобразуется через `Wide(text)` и передаётся в `HandleControl`.
2. `HandleControl` разбивает строку по `|` и выбирает действие по первому полю. Неизвестная команда даёт `ERR|неизвестная команда`.
3. `StartSession` читает размер (`ParseUll`), CRC (`wcstoul` с основанием 16) и очищает имя (`SanitizeName`). Нулевой размер отвергается.
4. Условие `r_has && r_size == size && r_crc_expect == crc && r_name == name && file != INVALID_HANDLE_VALUE` проверяет, есть ли **тот же незавершённый сеанс**. Если да — `offset = r_received`. MAC не входит в это сравнение.
5. Если условие ложно, код открывает файл с `CREATE_ALWAYS` и сбрасывает счётчики. Такой вызов может обнулить старый файл с тем же именем. Если открытие не удалось, приёмник шлёт `ERR|файл не создан`.
6. `NotifyStatus(Format(L"READY|%llu", offset));` сообщает позицию отправителю. `READY|0` означает старт с нуля, `READY|65536` — продолжение после первых 64 КиБ.

## 4. `Data`: где реально отправляются байты

**Вложение `ble.cpp:1494–1569`, `1762–1786`** · [`StartWriteBlock`](ble.cpp#L1537) · [Цикл отправки](ble.cpp#L1805)

1. `SetFilePointerEx` передвигает позицию чтения на `cursor`. `ReadFile` кладёт очередную порцию в `buffer`; `got` — сколько байтов прочитано.
2. Если очередь `pending` заполнена, `FinishOldestWrite` разбирает результат самой старой WinRT-операции. Несколько операций могут идти одновременно; это не означает, что все их данные уже подтверждены приёмником.
3. `channels[ch_index++ % channels.size()]` выбирает доступную характеристику данных по кругу. `StartWriteBlock` собирает кадр: 4 байта смещения в little-endian и затем байты файла. Например, смещение 256 — `00 01 00 00`.
4. **Сама запись по BLE** (вложение `1513–1514`):

   ```cpp
   block.op = ch.WriteValueWithResultAsync(ToBuffer(frame.data(), frame.size()),
                                           GattWriteOption::WriteWithoutResponse);
   ```

5. `cursor += got` передвигает позицию следующей отправки. Эта строка **не увеличивает `acked`**. Успешный локальный вызов WinRT не доказывает, что другой ноутбук записал блок.

## 5. Приём блока и `ACK`

**Вложение `ble.cpp:2057–2106`, `2513–2559`** · [`OnDataWrite`](ble.cpp#L2100) · [`HandleData`](ble.cpp#L2556)

1. `OnDataWrite` копирует значение GATT-запроса и вызывает `deferral.Complete()` **до** помещения данных в очередь и записи на диск. `RxQueueMain` забирает кадр и вызывает `HandleData`.
2. `DecodeFrame(bytes.data(), bytes.size(), offset, payload, count)` извлекает смещение, указатель на полезные байты и их длину. Пустой или неразбираемый кадр отбрасывается.
3. `off == r_received`: это следующие нужные байты. `WriteFile` должен успешно записать всю порцию (`written == n`); только тогда увеличивается `r_received`. Затем цикл дописывает следующие непрерывные блоки из `r_out`.
4. `off > r_received`: в файле есть пропуск. Кадр буферизуется в `r_out`, непрерывная позиция пока не меняется.
5. `off < r_received`: это повтор уже пройденной позиции. Второй раз байты не пишутся; приёмник может снова подтвердить свой прогресс.

Пример: пришли `[0, 100)`, потом `[200, 300)`. Приёмник может сказать только `ACK|100`. Когда придёт `[100, 200)`, он запишет его, затем допишет буферизованный `[200, 300)` и сможет сказать `ACK|300`.

**Вложение `ble.cpp:2575–2587`, `2224–2284`, `976–998`** · [Отправка уведомления](ble.cpp#L2267) · [Разбор ответа](ble.cpp#L1019)

- После очередного принятого блока пороги для планирования ACK — `kAckBytes = 3060` байт или `kAckIntervalMs = 800` мс. Проверка интервала в `HandleData` выполняется при обработке блока, а не гарантирует ACK каждые 800 мс в отсутствие данных.
- `SignalAck(acknowledged)` передаёт смещение потоку `AckWorker`. Тот формирует `ACK|смещение`, а `NotifyStatus` отправляет уведомление через `NotifyValueAsync`.
- `OnValueChanged` принимает уведомление у отправителя. `HandleStatusLine` применяет `if (value > acked) acked = value;`: запоздалый меньший `ACK` не откатывает прогресс.

## 6. Что происходит при сбое, обрыве и отмене

**Вложение `ble.cpp:1727–1759`, `1931–1999`, `3194–3200`** · [Окно и повтор](ble.cpp#L1770) · [Переподключение](ble.cpp#L1974) · [Отмена](ble.cpp#L3237)

- **Есть связь, но ACK не продвигается.** Окно ограничивает разницу `cursor − ack_now`. После остановки прогресса на `kStallMs = 1500` мс при наличии неподтверждённых байтов код делает `cursor = ack_now` и уменьшает окно. Он повторяет **неподтверждённый участок**, не обязательно весь файл.
- **Связь потеряна.** `SendJob` обрабатывает `LinkLost` или `Stall`, сбрасывает старое соединение и при наличии оставшихся попыток подключается заново. Новый `START` сам по себе не значит «с нуля»: решает ответ `READY`. Если приёмник сохранил открытый сеанс, он вернёт `r_received`. Если сменился временный BLE-адрес приёмника, попытка по сохранённому адресу может не сработать; нужен новый поиск.
- **Нажали «Отменить».** `Engine::Cancel` выставляет `cancel` и будит ожидающий поток. В ветке `Cancelled` вызывается `AbortRemote`: при доступном соединении он пробует послать `ABORT`. Если команда дошла, `AbortSession` (вложение с 2491) закрывает файл и сбрасывает живой сеанс, затем выдаёт `ABORTED`. Следующая передача обычно начинается с нуля; отмена — не пауза. Если `ABORT` не дошёл, нельзя считать, что приёмник сбросил сеанс.
- **Выключили только Wi-Fi.** Это не команда протокола и само по себе не должно останавливать передачу по BLE.

## 7. `SYNC`, `END` и `DONE`: доказательство завершения

**Вложение `ble.cpp:1810–1849`, `2413–2455`, `2482–2489`** · [Отправка `END`](ble.cpp#L1883) · [`FinishSession`](ble.cpp#L2456) · [`SyncStatus`](ble.cpp#L2525)

1. Отправитель сначала разбирает оставшиеся записи `pending`, затем ждёт подтверждения до размера файла. Если последнего ACK нет, периодически посылает `WriteControl(L"SYNC")`.
2. `SyncStatus` читает `r_received` под мьютексом и отвечает `ACK|смещение`. Эта команда **не пишет байты** и **не проверяет CRC**.
3. `WriteControl(Format(L"END|%llu|%08X", size, crc))` сообщает, что отправитель дошёл до конца. Приёмник берёт ожидаемые размер и CRC из сохранённого `START`: `FinishSession` не использует поля пришедшего `END` для сравнения.
4. `FinishSession` закрывает дескриптор и перечитывает принятый файл. Вот точное сравнение (вложение `2440–2441`):

   ```cpp
   const unsigned int actual = Crc32File(path, &file_size, nullptr);
   const bool ok = (file_size == size) && (actual == expected);
   ```

   `expected` — CRC исходника, сообщённая в `START`; `actual` — CRC сохранённого файла. Оба равенства должны быть истинными.
5. Приёмник отвечает `DONE|размер|CRC|OK|путь` или `DONE|размер|CRC|MISMATCH|путь`. Отправитель ждёт `DONE` до 30 секунд и проверяет `ok = match && remote_crc == crc;`. `MISMATCH` — итоговая ошибка, не обычный обрыв связи.
6. Если `DONE` потерялся уже после проверки, повторная попытка может пойти с нуля: приёмник уже закрыл сеанс. Это пограничный случай текущей реализации, не обязательное поведение при обычном разрыве посреди файла.

`ERR|...` сообщает об ошибке протокола, например при неудачном создании файла. В текущем коде он журналируется; он не превращается автоматически в `READY` или `DONE`, поэтому ожидание нужного ответа может закончиться по таймауту.
