# Лабораторная работа №6, вариант 8 (А8)

**Передача файла по Bluetooth Low Energy через кастомный GATT-профиль.**
Write Without Response, контроль целостности CRC32, подтверждения (ACK),
прогресс/скорость/ETA, обработка разрыва связи и возобновление передачи.

Приложение — обычное Win32-приложение на C++17 с оформлением из ЛР №5
(тёмная тема, карточки, owner-draw контролы, журнал событий).

---

## 1. Что умеет

| Возможность | Реализация |
|---|---|
| Передача файла Central → Peripheral | GATT-характеристика `Data`, запись **Write Without Response** |
| Максимальная скорость | MTU 23…517, размер блока = `MTU − 3 − 4` байт (4 байта — смещение) |
| Целостность | CRC-32 (IEEE 802.3) всего файла: считает отправитель до передачи, приёмник — после записи на диск |
| Подтверждение приёма | Notify-характеристика `Status`: `ACK\|смещение` примерно раз в 8 КБ или 100 мс |
| Прогресс, скорость, ETA | окно подтверждений, скользящая оценка скорости за 1,5 с, ETA = остаток / скорость |
| Разрыв связи | сеанс на приёмнике сохраняется; отправитель повторяет подключение (до 6 попыток) |
| Возобновление | повторный `START` возвращает уже принятую длину файла — передача продолжается с этого байта |
| Потери/дубликаты блоков | в каждом блоке 4-байтное смещение; приёмник принимает только блок с ожидаемым смещением, иначе сообщает своё |
| Журнал | цветной журнал в окне + файл `ble_log.txt`, отчёт `report_ГГГГММДД_ЧЧММСС.txt` |

Ограничения: один Central на приёмник, размер файла до 4 ГБ (смещение в кадре 32-битное).

---

## 2. Роли

Приложение умеет работать в двух ролях (переключаются в карточке «Сеанс»):

* **Отправитель (GATT Central)** — `BluetoothLEAdvertisementWatcher` ищет
  LE-устройства, `BluetoothLEDevice` + GATT-клиент подключается, находит
  кастомный сервис и передаёт файл.
* **Приёмник (GATT Peripheral)** — `GattServiceProvider` публикует сервис и
  включает BLE-рекламу, принимает write-запросы, пишет файл в
  `Документы\Lab6_BLE`, проверяет CRC32 и отправляет подтверждения.

> Для приёмника нужен адаптер и драйвер с поддержкой роли Peripheral
> (Windows 10 1809+, обычный Microsoft-драйвер). Если роль недоступна,
> в журнале появится сообщение `Не удалось создать GATT-сервис: …`.

## 3. Протокол

```
Сервис   A1B2C3D4-5E6F-4A7B-8C9D-0E1F2A3B4C5D
  Control  A1B2C3D4-5E6F-4A7B-8C9D-0E1F2A3B4C61  write / write-without-response
  Data     A1B2C3D4-5E6F-4A7B-8C9D-0E1F2A3B4C62  write-without-response
  Status   A1B2C3D4-5E6F-4A7B-8C9D-0E1F2A3B4C63  notify + read
```

Control (UTF-8, текстовые строки):

| Команда | Смысл | Ответ в Status |
|---|---|---|
| `START\|размер\|crc32\|имя` | начать/продолжить передачу | `READY\|смещение` |
| `SYNC` | «пришли текущее смещение» (перед `END`) | `ACK\|смещение` |
| `END\|размер\|crc32` | файл передан, проверить CRC | `DONE\|размер\|crc\|OK\|путь` или `DONE\|…\|MISMATCH\|путь` |
| `ABORT` | отмена | `ABORTED` |

Data (бинарный кадр):

```
+----------+----------------------+
| offset   |  данные файла        |
| uint32LE |  до MTU-3-4 байт     |
+----------+----------------------+
```

Status (уведомления):

```
ACK|<подтверждённое смещение>     — раз в ~8 КБ или 100 мс
READY|…  DONE|…  ABORTED  ERR|…
```

### Почему так

`Write Without Response` не даёт ответа на каждый блок, поэтому:

1. смещение в кадре позволяет приёмнику отбросить дубликат или блок «из
   будущего» (потерянный в буфере контроллера), не испортив файл;
2. отправитель держит окно (не более ~24 блоков / 8 КБ без подтверждения) —
   это flow control;
3. если подтверждение не двигается, отправитель откатывается к последнему
   подтверждённому смещению и повторяет блоки;
4. `START` с теми же (имя, размер, CRC) продолжает уже начатый сеанс.

## 4. Сборка

Требуется **Windows 10/11 (1809+)**, **Visual Studio 2022** с рабочей
нагрузкой «Разработка классических приложений на C++» и компонентом
**C++/WinRT**, Windows SDK 10.0.17763 или новее.

1. Открыть `Lab6_BLE.sln` (или сам `Lab6_BLE.vcxproj`).
2. Выбрать `x64` и `Debug`/`Release`, собрать (`Ctrl+Shift+B`).
3. Готовый файл — `bin\x64\<конфигурация>\Lab6_BLE.exe`.

Проект сам подключает C++/WinRT (`<CppWinRTEnabled>true</CppWinRTEnabled>`) и
`windowsapp.lib`; внешних библиотек (OpenCV и т.п.) не требуется.

Если VS не находит C++/WinRT-проекцию, установите компонент
«C++/WinRT» в Visual Studio Installer либо NuGet-пакет
`Microsoft.Windows.CppWinRT`.

### Особенности, уже учтённые в проекте

| Симптом при сборке | Причина и что сделано |
|---|---|
| `static assertion failed: STL1011 … /await … <experimental/resumable> deprecated` | заголовки C++/WinRT подтягивают экспериментальные корутины; в проекте задан `_SILENCE_EXPERIMENTAL_COROUTINE_DEPRECATION_WARNINGS` и `stdcpp17` |
| `непредвиденный здесь элемент "IInspectable"` | в обработчиках событий C++/WinRT второй параметр имеет тип `Windows::Foundation::IInspectable`; он указан полностью, без `using namespace` |
| `'Rssi' не является членом BluetoothLEAdvertisementReceivedEventArgs` | в WinRT свойство называется `RawSignalStrengthInDBm()` |
| `GetOpenFileNameW`/`OPENFILENAMEW`/`OFN_*` не объявлены | нужен `<commdlg.h>` — подключён в `main.cpp` |
| `'IsMultiAdvertisementSupported' не является членом BluetoothAdapter` | такого свойства в WinRT нет (есть `IsAdvertisementOffloadSupported`); в журнал выводятся BLE/Central/Peripheral |
| `аргумент: преобразование "float" в "int"` ×8 | `theme::Radius` был `float`, а `S()` принимает DIP-целое; радиус объявлен как `int`, деление идёт после `S()` |

## 4.1. Что даёт Windows, а чего нет

Программа не «дёргает» железо напрямую — она работает через системный
Bluetooth-стек (`Windows.Devices.Bluetooth`), а это единственный
поддерживаемый способ делать BLE из обычного Win32-приложения: без
драйверов, без прав администратора, без MSIX-пакета.

**Доступно полностью (Windows 10 1809+, Windows 11 — одинаково):**

| Возможность | API |
|---|---|
| Сканирование и разбор рекламы | `BluetoothLEAdvertisementWatcher` |
| Подключение, чтение/запись, уведомления | `BluetoothLEDevice` + `GattCharacteristic` |
| Write Without Response | `GattWriteOption::WriteWithoutResponse` |
| Свой GATT-сервер + реклама (роль Peripheral) | `GattServiceProvider` |
| Согласованный MTU | `GattSession::MaxPduSize()` |

**Чего нет (и обойти нельзя):**

* **Сырого доступа к HCI** — нельзя задать интервал соединения, supervision
  timeout, PHY (1M/2M/Coded), мощность передатчика, нельзя слать свои
  ATT-пакеты: всё только через GATT-API. (В Windows 11 появился
  `BluetoothLEPreferredConnectionParameters` — это *просьба* к стеку, не
  гарантия.)
* **L2CAP CoC** — публичного API нет, поэтому максимальная скорость
  ограничена GATT-записями.
* **Роли Peripheral на любом адаптере** — если драйвер/адаптер её не умеет,
  реклама и GATT-сервер не запустятся в принципе. Обычно умеют встроенные
  Intel/Realtek/MediaTek с драйвером Microsoft; дешёвые USB-донглы со
  сторонним стеком (CSR Harmony и подобные) — часто только Central.

**Что из этого следует на практике:**

* Блок данных = MTU − 3 − 4 байта, то есть 16…510 байт (MTU 23…517).
  Реальная скорость — десятки КБ/с: она определяется интервалом соединения
  (~30–50 мс), который назначает Central, и не настраивается из программы.
* Соединение всегда инициирует Central; Peripheral сам подключиться не может.
* Приёмник ограничен одним Central и 4 ГиБ на файл (32-битное смещение).

Поэтому программа при старте сканирования или приёма сама проверяет адаптер
и пишет в журнал его возможности:

```
Адаптер: BLE — да, Central — да, Peripheral — да, несколько реклам — да
```

Если роль Peripheral не поддерживается, выводится понятное объяснение
вместо невнятной ошибки `HRESULT`, а кнопка «Старт» не запускает рекламу.

**Если Peripheral не поддерживается вашим адаптером:** взять другой ПК
(встроенный адаптер ноутбука почти всегда умеет обе роли) — роли в программе
переключаются, отправителем может быть любой Central, в том числе смартфон
с nRF Connect.

## 5. Как проверить (нужны два устройства с Bluetooth)

**Компьютер A — приёмник**

1. Роль: «Приёмник (Peripheral)».
2. «Старт» → в журнале `GATT-сервис опубликован. Идёт BLE-реклама…`.
3. В системе компьютер виден под своим именем (например, `DESKTOP-1234`).

**Компьютер B — отправитель**

1. Роль: «Отправитель (Central)».
2. «Поиск» → в списке появятся LE-устройства; у нужного будет пометка
   `• Lab6` (в рекламе есть UUID нашего сервиса).
3. Выбрать устройство → «Подключить». В журнале: `Подключено: …, MTU 517,
   блок данных 510 байт`.
4. Выбрать файл («Обзор…» или перетащить в окно) → «Отправить».

В процессе: полоса прогресса, «Передано», «Скорость», «Осталось», счётчик
блоков и ACK, график скорости. По завершении — сравнение CRC32 и строка
`Готово: … CRC32 … совпал`.

**Проверка возобновления:** во время передачи выключить Bluetooth на
приёмнике (или выключить его совсем). Отправитель покажет «Связь потеряна —
восстановление…» и будет пытаться подключиться; включите приёмник обратно —
передача продолжится с уже принятого байта, в журнале будет
`Приёмник принял ранее N — продолжаем`. Итоговый CRC32 должен совпасть.

**Проверка отмены:** «Отменить» → отправитель пришлёт `ABORT`, приёмник
оставит частичный файл, в журнале — соответствующая запись.

Тест без второго ПК: приёмник можно проверить любым BLE-сканером
(например, nRF Connect — виден сервис и три характеристики), а передачу
файла — только с нашего отправителя (нужен формат кадров).

## 6. Структура кода

| Файл | Назначение |
|---|---|
| `main.cpp` | окно, команды, модель для отрисовки, журнал и отчёт |
| `ble.cpp` / `ble.h` | весь Bluetooth LE: сканирование, GATT-клиент, GATT-сервер, протокол передачи, CRC, окно подтверждений, восстановление связи |
| `visual.cpp` / `visual.h` | тема, шрифты, раскладка, отрисовка (GDI+), owner-draw |
| `crc32.h` | CRC-32 (таблица строится на этапе компиляции) |
| `protocol.h` | чистые примитивы протокола: разбор строк, кадр Data, имя файла — без Win32, покрыты тестами |
| `tests/protocol_test.cpp` | автотесты: CRC, кадры, разбор строк, модель передачи с потерями и возобновлением |
| `САМОПРОВЕРКА.md` | отчёт самопроверки: что проверено, чем и что осталось на оборудование |
| `app.rc`, `app.ico` | значок и сведения о файле |

Потоки: UI-поток никогда не вызывает WinRT. Движок работает в отдельных
MTA-потоках (сканирование, подключение/передача, GATT-сервер) и общается с
окном через `PostMessage` и снимки состояния под `std::mutex`.

## 7. Автотесты

Протокольная часть (CRC-32, кадры `Data`, разбор `START/READY/ACK/DONE`,
санитизация имени, модель передачи с потерями, дубликатами и возобновлением)
проверяется без Bluetooth и без Windows:

```bash
g++ -std=c++17 -O2 tests/protocol_test.cpp -o protocol_test && ./protocol_test
# или в среде MSVC:
cl /EHsc /std:c++17 tests\protocol_test.cpp
```

Ожидаемый результат: `Проверок: 90, ошибок: 0`, `РЕЗУЛЬТАТ: OK`.
Подробный отчёт о самопроверке — в `САМОПРОВЕРКА.md`.
